# Part 4A: Wallet financial foundation

1. **Files changed.** Added `src/models/WalletTransaction.js`, `src/services/wallet.service.js`, `src/services/reward-approval.service.js`, `src/scripts/helpers/walletHarness.js`, `src/scripts/testWalletFoundation.js`, and this report. Updated `src/models/Reward.js`, `src/controllers/reward.controller.js`, `src/services/review-reward.service.js`, `src/scripts/auditReviewRewards.js`, and `src/scripts/testReviewSecurity.js`. Paths are relative to backend. Existing unrelated working-tree changes were preserved.

2. **Mutation audit.** Two production balance writes existed: admin reward approval incremented User separately from Reward.save; review rewards incremented User in the review transaction. Both now call the shared service. The only production walletBalance mutation is the conditional increment in wallet.service.js. User schema retains its zero default. Auth/profile responses and admin reward population only read balance; profile validation allows selected profile fields. No manual wallet-adjustment path or customer wallet-history endpoint was found. Returns/refunds do not mutate wallet. Existing Order methods remain COD/ONLINE.

3. **Schema.** WalletTransaction stores user, optional exact order/reward/refund references, reversalOf, purpose, direction, positive amount, INR currency, POSTED status, idempotencyKey, balanceBefore, balanceAfter, reason and createdAt. Reward gains walletTransaction. Financial fields are immutable; validation checks balance arithmetic and purpose-specific attribution. Existing-document save, update, replace, delete, bulkWrite and insertMany are blocked. New saves require an active transaction. These are application/Mongoose protections: raw collection access or privileged database administration can bypass them and must be restricted operationally.

4. **Purposes and money.** REWARD_CREDIT/CREDIT requires Reward; ORDER_PAYMENT/DEBIT requires Order; ORDER_REFUND/CREDIT requires Order and RefundTransaction; REVERSAL references the original and carries its attribution. No generic adjustment purpose was invented. Wallet rewards and balances use INR; new postings require positive safe whole-INR integers. Existing fractional legacy balances are preserved and fail closed for posting, rather than rounded. RefundTransaction also has a paise representation: future refund integration must explicitly address fractional amounts without passing paise as INR.

5. **Credit.** creditWallet validates server inputs, joins an active caller transaction or owns a withTransaction boundary, checks idempotency, conditionally increments the exact User, obtains the pre-update balance and creates the ledger entry in the same transaction. Overflow or malformed legacy balances reject. Externally supplied sessions must be in a transaction; callers must propagate failures and abort, as both reward integrations do.

6. **Debit.** debitWallet uses the same boundary with an atomic conditional User update requiring walletBalance >= amount. The returned preimage determines before/after values. Concurrent writes contend on the same User document and MongoDB transaction retries re-evaluate the condition; there is no blind read/save deduction.

7. **Insufficient funds.** A debit below the requested balance fails with 409, without a partial debit or posted entry. Ledger creation failure rolls the balance update back. Credit reversals use the same conditional debit protection.

8. **Idempotency.** Unique user + idempotencyKey scopes retries. Matching retries return the existing posting; mismatched amount, purpose, direction, reason or references return a conflict. Unique reward attribution independently prevents duplicate reward credit. Owned transactions recover duplicate-key races through read-only ledger queries after rollback. External callers retain transaction ownership and error propagation.

9. **Reward refactor.** Reward remains the business record. Both reward paths use canonical reward-credit:<Reward ID> keys, persisted reward values, REWARD_CREDIT entries and exact reciprocal Reward/ledger links. Existing reward amounts and eligibility rules are preserved.

10. **Admin approval.** Reward status, creditedAt, walletTransaction, User balance and ledger commit together. Repeated approval/status toggles cannot recredit a marked reward. Historical Approved rows missing creditedAt are ambiguous and reject status changes until reconciled, preventing a reject/reapprove bypass. Existing credited legacy rows are not credited again or given fabricated postings. Notification/email remains after transaction commit.

11. **Review reward.** Existing review transaction now includes shared credit, Reward linkage and creditedAt. The INR 10 reward, eligibility and duplicate-review protections remain. Tests verify review/reward/balance/ledger rollback on failures and no duplicate financial credit.

12. **Reversal.** reverseWalletTransaction derives amount and opposite direction from the original posting for the exact user; requires a reason and references the original. A unique reversalOf prevents a second compensation, including different retry keys. Reversals cannot themselves be reversed. Original CREDIT reversal requires explicit internal allowCreditReversal authorization and sufficient balance. No public endpoint exposes this primitive; future business callers must enforce authorization before enabling that flag.

13. **Legacy balances.** No reset, startup backfill, fabricated ledger history or migration was performed. Existing balances remain authoritative. Ambiguous credited history requires reconciliation rather than an automatic additional credit.

14. **Reconciliation.** reconcileWallet reads balance and chronological ledger in a transaction. It checks arithmetic, chain continuity and current balance, reports net change and inferred opening balance, and optionally compares a supplied baseline. Without an explicit baseline, ledgerDerivedBalance is null. historicalReconciliationComplete remains false: a matching inferred or supplied balance is not proof of history. auditReviewRewards now reports ledger reconciliation and treats historical credited Reward totals as informational, since debits/reversals invalidate the old reward-sum-equals-balance assumption. The audit script was not executed against a database. Later migration should freeze/cut over writers, snapshot balances and reward history, resolve discrepancies, approve documented per-user opening balances, and use a separate audited idempotent baseline migration. An opening-balance purpose/schema is deliberately deferred.

15. **Indexes/deployment.** WalletTransaction declares unique (user,idempotencyKey), unique partial reward for REWARD_CREDIT, unique partial reversalOf, (user,createdAt,_id), and (order,createdAt). Deploy and verify these indexes before enabling the changed writers; do not assume model declarations mean production indexes exist. Preserve the existing unique review-reward index and inspect legacy duplicates before building any affected index. Transactions require a MongoDB replica set or supported sharded deployment. No index creation, syncIndexes or DB migration was run here. A real replica-set integration test remains a deployment prerequisite for validating actual contention/retries.

16. **Security.** No new routes were added. Customer input cannot directly invoke wallet primitives or set authoritative before/after balances/status; profile allowlists remain in place. Admin approval uses stored Reward values and existing admin route protection. Review amount is a server constant. Future Order payment/refund callers must validate ownership, eligibility and authoritative amounts within their business transaction: the internal foundation validates reference shape, not future Order business rules.
